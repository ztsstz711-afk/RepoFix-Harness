# V3.3 test evidence provenance

## Problem

V3.2 correctly invalidated stale pytest evidence after each changed patch, but it assumed every `run_command` observation was a completed pytest result. The tool runtime allows only pytest. When a model requested `sed -n ...` or `python -c ...`, the permission layer returned a failed observation without launching a process. Context interpreted that tool rejection as a failed focused test and entered revision state.

This distinction matters because a tool policy failure says nothing about the current patch.

## Evidence predicate

V3.3 centralizes one predicate for `run_command` history:

- `metadata.return_code` present: pytest executed and its pass/fail result is evidence;
- `metadata.timed_out=true`: pytest started but timed out, so the failed verification is evidence;
- non-empty metadata without either marker: command did not produce an execution result and is not test evidence;
- empty metadata: accepted for backward compatibility with old checkpoints and deterministic fixtures created before execution metadata was persisted.

Automatic `post_patch_test` metadata remains explicit current evidence and does not use this predicate.

The same decision now controls baseline supersession, progress summary, repair phase, revision navigation cap, and revision working-set selection. Denied actions remain visible in the complete trace for debugging and repeated-action controls.

## Deterministic coverage

Focused tests verify that:

1. a denied non-pytest command after a patch remains `patch_needs_verification`;
2. the denied action does not create a revision cap or working set;
3. a real failed pytest with `return_code=1` still enters `patch_needs_revision`;
4. a denied action does not hide the independent baseline;
5. legacy run-command events with empty metadata retain their previous semantics.

## Frozen real-model follow-up

The follow-up repeated the same three-trial upstream h11 gate used for V3.1 and V3.2: identical source snapshot, task, Docker commands, DeepSeek non-thinking mode, 60,000-token limit, and 12-request limit. It used a new manifest and output directory.

Trial 03 completed normally and passed the full 78-test h11 acceptance suite. Trials 01 and 02 both executed real focused pytest after their second changed patch; those tests still failed, and each run later stopped at the token reserve. No denied command was misclassified in these sampled trajectories, so the deterministic coverage remains the direct validation of that mechanism.

The gate is better than V3.2's independent 0/3 result but below V3.1's 2/3 result. These are three-trial engineering gates, not a stable model success-rate estimate. The two failures also show the next measured cost issue: `patch_needs_verification` restored full pre-patch history, producing 22,247 and 23,907-character verification contexts even though the phase policy allowed only focused test and Git inspection actions.
