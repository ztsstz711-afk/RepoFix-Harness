# V0.9 Regression suite

V0.9 shifts the project from adding Harness features to measuring repair behavior across distinct bug classes.

## Scenarios

| Task | Bug class | Baseline | Expected implementation file |
|---|---|---:|---|
| `toy-add` | Wrong arithmetic operator | 1 failed | `calculator.py` |
| `username-normalization` | Cross-file string normalization | 1 failed | `formatter.py` |
| `optional-config-override` | `None` versus meaningful override semantics | 1 failed, 1 passed | `config_loader.py` |
| `one-based-pagination` | Boundary/off-by-one error | 2 failed, 1 passed | `pagination.py` |
| `exact-inventory-boundary` | Package navigation and inclusive boundary | 1 failed, 2 passed | `inventory/policy.py` |

Every source fixture remains intentionally buggy. `EvaluationRunner` copies each repository into a temporary workspace before the Agent starts.

## Two independent metrics

Passing pytest is necessary but not sufficient. Each task may declare `expected_changed_files`, which is kept out of the model prompt. The report adds:

- `change_scope_evaluated`
- `change_scope_matches`
- `change_scope_rate`

This distinguishes a minimal repair from a broad patch that happens to pass the tests.

## Offline validation

Scripted providers apply the known minimal repair for each fixture solely to validate evaluation plumbing. The offline suite currently achieves 5/5 test success and 5/5 change-scope matches in isolated workspaces. These providers are test fixtures; `repofix-eval` continues to instantiate the real OpenAI-compatible API provider.

## Real-model gate

The next milestone is a real five-task run with fixed request and token budgets. Based on earlier Gemini runs, this likely exceeds the practical daily free-tier request allowance, so provider switching should happen immediately before that benchmark rather than during fixture development.
