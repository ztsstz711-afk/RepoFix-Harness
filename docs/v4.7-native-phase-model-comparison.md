# V4.7 native phase model comparison

## Goal

V4.6 证明真实 Provider 路径可以原生生成 schema-v3 phase telemetry。V4.7 继续回答两个更具体的问题：

1. 同一组真实轨迹能否通过严格身份校验做 Flash/Pro 对照；
2. 总 requests/tokens 的差异能否自动归因到每个案例的具体 repair phase。

比较报告现在不仅显示 overall phase delta，还会为每个 case 输出 snapshot、target-read grace 和非零 phase delta。

## Frozen contract

两组运行共享同一个 `evals/native-phase-model-comparison-v4.7.json`：

| Case | Request cap | Token cap | Verification |
|---|---:|---:|---|
| Toy addition | 8 | 12,000 | Docker full pytest |
| Username normalization | 8 | 16,000 | Docker full pytest |
| Optional config override | 8 | 16,000 | Docker full pytest |

两组都使用 `thinking=disabled`、原生 tool calling、JSON fallback、2,048 普通输出上限和 4,096 patch 输出上限。每组最多授权 24 requests，所有 task 均启用 patch 后自动定向验证并预先声明期望改动文件。

唯一实验变量是模型：`deepseek-v4-flash` 与 `deepseek-v4-pro`。

## Results

| Metric | Flash | Pro | Pro delta |
|---|---:|---:|---:|
| Verified repairs | 3/3 | 3/3 | 0 |
| Exact change scopes | 3/3 | 3/3 | 0 |
| Requests | 11 | 8 | -27.27% |
| Tokens | 21,295 | 13,074 | -38.61% |
| Provider retries | 0 | 0 | 0 |
| Estimated peak cost | $0.00847512 | $0.01649349 | +94.61% |

成功率在这组三个小案例上已经饱和。Pro 路径更短，但更高单价使实际估算成本接近 Flash 的两倍。

## Per-case attribution

| Case | Pro snapshot delta | Non-zero phase deltas |
|---|---:|---|
| Optional config override | -3 | `ready_to_patch -1`, `patch_needs_revision -1`, `patch_due -1` |
| Toy addition | +1 | `inspecting +1` |
| Username normalization | -1 | `inspecting -1` |

整体少 3 个决策 snapshots 并不表示 Pro 在每个案例都更短。它在 toy case 多一次 inspection，在 username case 少一次 inspection；主要差异来自 optional-config：Flash 的首次补丁未通过自动 pytest，进入 revision 后再次修改，Pro 则一次补丁通过。V4.7 因而能把总量差异定位到具体案例与阶段，而不是把它误解为普遍推理优势。

## Interpretation

这是三个自建 fixture、每模型单次的机制门禁，不是模型排行榜，也不能估计真实仓库修复胜率。结果支持两个有限结论：

- schema-v3 phase telemetry 已能在同版本真实模型对照中工作，并提供逐案例阶段归因；
- 对这组三个低成本任务，Pro 减少请求和 tokens，但没有增加成功数且成本更高，因此 RepoFix 默认模型继续保持 Flash。
