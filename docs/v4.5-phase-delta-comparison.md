# V4.5 phase-delta comparison

## Goal

Resource totals show whether a candidate used fewer requests, but not why. V4.5 extends strict identity-compatible model and thinking comparisons with:

- overall snapshot, target-read activation, phase-count, and transition deltas;
- the same delta object for every evaluation case;
- a concise Markdown view of non-zero phase counts and per-case snapshot differences.

Every value is `candidate - baseline`. Positive values mean the candidate used more decision snapshots. Phase deltas are emitted only when both validated reports contain schema-v3 telemetry; historical reports without it retain the existing success/resource comparison.

## Frozen Click backfill

The V3.7 Click Flash and Pro reports predate `target_read_grace`. Their immutable files were not changed. In memory, the missing flag was deterministically derived from `repair_phase`; because `target_read_due` did not exist in that Harness, every derived value was false. Both reports were then validated as schema-v3 objects before comparison.

Both models had already completed 3/3 verified repairs with exact scope. The phase delta explains the recorded 16-to-10 request reduction:

| Candidate Pro minus baseline Flash | Delta |
|---|---:|
| Total decision snapshots | -6 |
| `locating` | 0 |
| `inspecting` | 0 |
| `ready_to_patch` | -3 |
| `patch_attempt_failed` | -3 |
| `verified_patch` | 0 |
| Target-read activations | 0 |

The Pro advantage did not come from fewer initial locating or inspecting actions. Flash entered a patch-ready state and then a rejected-patch recovery path once per trial; Pro moved from inspection directly to a verified patch in two trials and avoided all three rejected-patch snapshots.

## Scope

This is retrospective attribution over a frozen three-trial comparison, not evidence that Pro universally writes better patches. The next gate should generate schema-v3 telemetry natively across multiple cases and variants.
