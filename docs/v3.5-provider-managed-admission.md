# V3.5 provider-managed residual admission

## Problem

AgentLoop and the OpenAI-compatible Provider both protected the same run-level token boundary. AgentLoop first estimated a compact working-set request as `ceil(context_chars / 3) + 2,000`. If that estimate did not fit, it stopped before giving Provider the exact remaining allowance. Provider never had a chance to calculate the complete system, user, and tool-schema prompt or reduce the action output ceiling.

In the V3.4 auto-verification follow-up, Trial 02 had 6,611 tokens remaining and a 6,758-token AgentLoop estimate. Replaying the exact frozen history with API calls disabled showed that Provider's full residual check would admit the request and reduce output as needed.

## Admission ownership

V3.5 delegates residual admission only when both conditions hold:

1. a phase working set is active, so the current prompt intentionally supersedes the historical request average;
2. the provider implements `limit_next_action_tokens`, explicitly accepting the exact remaining run allowance.

AgentLoop still checks whether the request or token budget is already exhausted. It then records the context snapshot and passes the remaining tokens to Provider. The OpenAI-compatible Provider estimates the complete prompt, requires at least 256 output tokens, shrinks the configured output ceiling when necessary, and raises `ModelTokenLimitReached` before making an API call if the minimum request cannot fit.

Ordinary contexts, historical-average protection, providers without the limit interface, maximum requests, maximum tokens, and budget-boundary independent final verification are unchanged. Each snapshot records `provider_managed_token_admission` for auditability.

## Deterministic evidence

- A bounded-provider integration trajectory spends 900 of 1,000 tokens on its first patch, enters the verification working set, receives the exact remaining allowance of 100, and is reached instead of being preempted by AgentLoop.
- The provider's simulated 120-token refusal remains `token_budget_reserve`; the run does not exceed 1,000 tokens.
- The exact V3.4 follow-up Trial 02 history, 14,180-character revision context, and 6,611-token allowance reach the Provider request boundary in an offline replay instead of triggering Provider's pre-request refusal.

## Frozen gate

The V3.5 gate keeps `verify_after_patch=true` and all source, model, Docker, task, request, and token settings identical to the V3.4 auto-verification follow-up. This isolates provider-managed residual admission under the configuration that exposed the 147-token disagreement. Results are reported separately.
