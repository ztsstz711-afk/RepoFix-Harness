# V3.0 residual-budget format recovery

## Problem

V2.9 successfully moved all three 60k h11 trajectories into a forced revision request after one evidence read. The ninth response in each trial violated the active patch contract: one attempted a disallowed read and two emitted identical `old_text` and `new_text`.

Provider recovery previously estimated every corrective request as:

```text
previous observed input tokens + configured phase output ceiling
```

For `patch_due`, the configured output ceiling is 4,096 tokens. The three trials had 6,911, 9,528, and 7,544 tokens left, while the corresponding full retry estimates were 11,246, 11,099, and 10,741. All retries were therefore denied before a request. This preserves the hard budget but can strand enough residual capacity for a smaller correction.

## Policy

V3.0 keeps the first request and normal retries unchanged when the full allowance fits. Near the run boundary, a format retry now:

1. estimates the next input from the previous observed input plus a conservative one-token-per-three-characters allowance for the appended correction;
2. subtracts that estimate from the remaining run-level token budget;
3. caps the next request's output at the smaller of the normal phase ceiling and the residual amount;
4. requires at least 256 output tokens, or refuses the request before calling the provider.

The per-retry output cap is reset for every new Agent action. It never increases the configured output limit and never changes the run's `max_tokens`. When reduced, `format_retry_output_tokens:<limit>` is persisted in provider diagnostics.

## Deterministic verification

Provider tests cover both boundaries:

- with enough residual budget for the repeated input and at least 256 output tokens, a malformed patch response is retried using a smaller `max_tokens` and can return a valid patch;
- when the remaining allowance cannot cover the estimated input plus the minimum output, `ModelTokenLimitReached` is raised before a second API request;
- request-count limits, transient retry accounting, native-tool fallback, JSON fallback, and the ordinary 4,096 patch allowance retain their existing tests.

## Scope and next gate

Dynamic retry output is a budget utilization mechanism, not permission to exceed a trial limit. It also cannot repair a semantically wrong patch by itself; it only gives the model a bounded chance to correct an invalid tool response. The following real-model gate tests the mechanism separately; the V2.9 0/3 result remains unchanged.

`evals/upstream-h11-chunk-footer-stability-v3.0.json` repeats the same checksum-qualified h11 case three times with `deepseek-v4-flash`, thinking disabled, 12 requests and 60,000 tokens per trial, Docker isolation, focused iteration, complete 78-test final acceptance, and exact scope limited to `h11/_readers.py`.

## Interpretation

V3.0 demonstrates that residual-budget recovery works as designed under a real provider and remains inside each 60k trial limit. It does not improve the observed repair result: 0/3 stayed 0/3, and trajectory variation raised total tokens above both V2.8 and V2.9 60k gates. The remaining bottleneck is the size and quality of the revision working set before a normal next action, not merely the output allowance of an internal format retry.
