# V4.9 held-out upstream evaluation plan

## Purpose

V4.8 measured breadth over bugs already used while developing RepoFix. V4.9 adds a stricter generalization check: three real upstream Python bugs that had never appeared in the repository, prompts, fixtures, or previous evaluations before the V4.8 result was frozen.

Each task receives one formal attempt. Tasks will not be replaced, selectively rerun, or given larger budgets after results are observed. A negative result remains part of the published report.

The parent snapshots fail their focused regression tests and the corresponding upstream fix snapshots pass them. Final acceptance commands also pass on every fix snapshot before any Agent run.

## Execution contract

- Harness: committed V4.8.0 state.
- Provider: the configured real OpenAI-compatible DeepSeek provider, thinking disabled.
- Isolation: Docker with network disabled during tests and a read-only final acceptance mount.
- Image: `repofix-pytest-heldout:v4.9`, built from [`sandbox/Dockerfile.heldout`](../sandbox/Dockerfile.heldout).
- Limits: 12 model requests and 18 steps per task; 32k, 36k, and 32k token ceilings.
- Verification: every focused baseline must fail, focused tests run after patches, and a larger independent acceptance suite determines success.
- Scope oracle: only the one upstream implementation file named in the manifest may change.

## Interpretation fixed before execution

The gate passes when at least 2/3 tasks are independently verified, every successful task has exact changed-file scope, and the schema-v3 report passes the internal aggregate validator. A 3/3 result is strong small-sample evidence; 2/3 is useful but identifies a concrete limitation; 0-1/3 means the held-out gate fails.

This is still a small custom benchmark and must not be described as SWE-bench. Unlike V4.8, however, it measures first-use performance on bugs not used to tune RepoFix's Harness behavior.
