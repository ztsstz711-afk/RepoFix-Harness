# V3.2 verification freshness

## Problem

V3.1's second frozen h11 trial followed this sequence:

1. write an initial patch;
2. run focused pytest and observe a failure;
3. inspect the failure and write a second changed patch;
4. continue as though the old failure still described the new code.

The second patch had never been tested. Nevertheless, repair phase, revision navigation cap, progress summary, and revision working-set selection all retained the earlier failed pytest. The phase policy therefore exposed revision tools instead of requiring focused verification. The trial consumed another model request and then stopped at the token reserve.

## State rule

V3.2 assigns test evidence to the workspace revision that produced it:

- a successful `apply_patch` with `changed=true` invalidates all earlier focused pytest evidence;
- without an automatic test on that patch, the next phase is `patch_needs_verification`;
- a failed `post_patch_test` on the same event is current evidence and enters `patch_needs_revision`;
- a passing `post_patch_test` on the same event is current evidence and enters `verified_patch`.

The rule is applied consistently to `_repair_phase`, `_revision_navigation_cap`, `_revision_working_set`, and the user-visible progress summary. It changes only prompt and phase state; complete history and trace artifacts remain immutable.

## Deterministic coverage

Three focused trajectories assert the important boundaries:

| Current patch evidence | Expected phase | Revision working set |
|---|---|---|
| no test after a changed revision | `patch_needs_verification` | inactive |
| same-patch automatic test failed | `patch_needs_revision` | active |
| same-patch automatic test passed | `verified_patch` | inactive |

The first case also requires `revision_navigation_cap=null` and reports `latest_agent_pytest=not run for current patch`, making the state visible to both the model and trace reviewers.

## Frozen follow-up

The real-model follow-up uses the same upstream h11 source snapshot, task wording, Docker test commands, DeepSeek non-thinking mode, 60,000-token run limit, 12-request limit, and three repetitions as V3.1. Its manifest and output directory are independent. The result is not combined with V3.1 or used to rewrite the earlier 2/3 outcome.
