# V1.5 upstream bug suite

## Goal

V1.5 从人工注入回归转向真实上游修复。一个案例只有同时满足以下条件才进入 suite：

1. 固定公开上游 repository、父 commit 和修复 commit。
2. 修复 commit 同时包含实现修改和可独立运行的回归测试。
3. buggy workspace 保留父 commit 的实现，只复制修复 commit 中的测试文件。
4. buggy 完整测试稳定失败，fixed reference 完整测试稳定通过。
5. 不需要网络、数据库或外部服务即可在受限 Docker 中验证。

这不是 SWE-bench。它是一个更小、可人工审计的真实 commit-level repair suite，用于先验证 RepoFix 对未知第三方代码和真实上游语义的适应能力。

## Offline qualification

Qualification used the same `repofix-pytest:latest` image as evaluation, with networking disabled, a read-only source mount, no capabilities, no privilege escalation, 512 MB memory, one CPU, and 256 PIDs.

| Case | Buggy focused test | Fixed focused test | Fixed full suite |
|---|---:|---:|---:|
| Negative `sliced()` size | 1 failed | 1 passed | 730 passed |
| Stable running min/max | 2 failed | 2 passed | 732 passed |
| Dotted key part limit | 1 failed | 1 passed | 17 passed |

The more-itertools runs additionally completed 19,938 subtests. The Tomli run completed 744 subtests. These counts establish a deterministic before/after oracle before any model request is authorized.

## Evaluation contract

- Docker execution only; no repository test code runs directly on the host.
- The independent baseline uses the smallest upstream regression test that reproduces the bug, giving the model a fast traceback-backed starting point.
- Every successful finish, budget-boundary salvage, malformed-output salvage, and post-rollback check uses the full upstream suite. A focused pass alone can never produce a successful run.
- One trial per case for the first gate.
- Maximum 12 requests per task; token limits are 32,000 for the smaller boundary case, 40,000 for the two-edit algorithm case, and 68,000 for the 1,009-file parser repository.
- Suite authorization: 36 requests total.
- Expected changed files are evaluation metadata and are never included in the model prompt.

The first gate is a feasibility measurement, not a success-rate benchmark. Repetitions and broader repositories should be added only after all three cases have deterministic environment behavior and at least one bounded end-to-end run.

An initial 24,000-token calibration gate completed the boundary case but stopped the other two at the pre-request reserve check. One had correctly changed the expected file but still needed a second symmetric edit and verification; the other had located the parser function but had not patched it. The revised limits preserve the 12-request and 36-request suite authorization while allowing realistic third-party repository navigation. The incomplete calibration output is retained locally and is not reported as a successful benchmark.

A second calibration completed both more-itertools cases but showed that Tomli's recursive listing spent context on hundreds of deeply nested TOML fixtures. V1.5 therefore bounds `list` output and sorts shallow source paths first. A later focused-baseline run reached the correct constant location at 47,653 tokens with exactly three authorized actions left, but the 56,000-token admission reserve could not admit the first patch action. The final parser ceiling is therefore 68,000 tokens, sized for the observed two localized patches plus focused verification while retaining the unchanged 12-request limit. This is a declared maximum rather than a target; request count, permissions, context size, output size, and Docker isolation remain independently bounded.

A later Tomli calibration exposed a separate harness problem: the full baseline sometimes reached its 90-second container timeout before returning any traceback, even though the same suite completed under lower host load. The two-tier verification contract fixes the information problem rather than increasing model budget. Tomli's focused regression takes roughly 1.5 seconds, while its 17-test/744-subtest final suite remains independently enforced with a 180-second timeout allowance.

## Designated release gate

The designated V1.5 gate was run once after the Harness, manifest, adaptive JSON-output behavior, and navigation budget were frozen. It is reported as a feasibility gate, not a statistically stable success rate.

| Case | Status | Steps | API requests | Tokens | Format retries | Changed files | Full-suite result |
|---|---:|---:|---:|---:|---:|---|---:|
| Negative `sliced()` size | success | 7 | 7 | 18,119 | 0 | `more_itertools/more.py` | 730 passed |
| Stable running min/max | success | 7 | 9 | 33,840 | 2 | `more_itertools/recipes.py` | 732 passed, 19,938 subtests passed |
| Dotted key part limit | budget exhausted | 11 | 11 | 64,018 | 0 | none | 1 failed, 16 passed, 744 subtests passed |

Aggregate result: **2/3 verified repairs**, **2/3 exact change-scope matches**, 27 of 36 authorized requests, 115,977 tokens, and a conservative estimated API cost of $0.04467383. Both successful tasks had failing focused baselines and passed their independent full upstream suites after the repair. The Tomli task exhausted its token-reserve admission check before writing a patch.

An exploratory pre-release run did repair Tomli, but another task in that run failed on empty JSON-mode output. Those calibration runs motivated adaptive JSON fallback; they are not combined with the designated gate or counted as a 3/3 result. The honest release conclusion is that V1.5 handles both more-itertools cases reliably in this gate, while the larger parser task remains trajectory-sensitive and requires better navigation efficiency rather than unbounded retries.
