# V1.3 multi-case context matrix

Run date: 2026-08-27  
Model: `deepseek-v4-flash`  
Suite: `evals/context-matrix.json`  
Execution backend: restricted Docker

The experiment compares failure-context seeding on and off across five deterministic Python repair cases. Each case/variant pair runs three times from a fresh repository copy, and trials are interleaved to reduce ordering effects. The matrix contains direct traceback targets as well as indirect cross-file faults where the failing test or imported facade is not the file that should be changed.

The complete 30-trial run used 148 API requests, including four JSON-format retries, and 218,295 tokens. It cost an estimated `$0.08099004`. There were no transient/network retries and no failed repair or scope result.

Across the 15 matched trial pairs, context-on used fewer requests in 10 pairs, tied in four, and used more in one. It used fewer tokens in 11 pairs and more in four.

An exact two-sided paired sign test (ties excluded) gives `p=0.01171875` for request direction and `p=0.11846924` for token direction. The request result is directionally consistent in this matrix; the token result is not strong enough to reject an equal-direction null at 0.05. These are exploratory checks across multiple related metrics, with no multiple-comparison correction, and should not be presented as confirmatory inference.

## Interpretation

Failure context improved aggregate efficiency without changing success or file-scope accuracy in this controlled matrix. The strongest gains occurred when traceback/import evidence pointed at the implementation that needed editing. The username case is a useful counterexample: the imported facade was not the faulty helper, so the extra evidence did not shorten navigation and slightly increased token use.

This is evidence for the Harness mechanism, not a broad model-quality benchmark. The fixtures are small and deterministic, there are only three repeats per cell, all trials use one model, and success is saturated at 100%. A larger external issue set is required before making general claims about repair accuracy.

The runner stores partial `progress.json` after every trial and isolates unexpected runner exceptions into per-trial `runner_error` results. New reports also include the exact manifest SHA-256 and a stable digest of each copied source tree, preventing comparisons between silently changed fixtures.
