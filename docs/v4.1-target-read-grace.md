# V4.1 search-hit target-read grace

## Failure pattern

V4.0's independent Pro follow-up produced three nearly identical 0/3 trajectories. In every trial, the fifth successful navigation action searched for `class Signer` and found it near line 271, while prior reads covered unrelated lines. The existing five-navigation cap immediately changed the phase to `patch_due`, which exposed only `apply_patch` before the model could read the target code.

All three trials inserted `# placeholder` beside `class Signer` to regain navigation, failed the focused test, removed the placeholder, and eventually exhausted 12 requests. This was a Harness incentive problem rather than evidence that more model reasoning or a larger token budget was needed.

## Change

V4.1 adds `target_read_due` when all conditions hold:

1. the first-patch navigation count has reached five;
2. the latest action is a successful search with at least one match;
3. the search output contains a source path and line number;
4. at least one matched line is outside all prior successful read ranges.

The central registry exposes only `read` and `apply_patch` in this phase. If the model reads, the next phase is immediately `patch_due`, so list/search cannot reopen and the grace cannot become an unbounded exploration loop. Already-read hits, empty searches, or unparseable output receive no grace.

## Offline replay

Replaying the first five history events from all three V4.0 failures changed the phase identically:

| Trial | V4.0 phase | V4.1 phase | Allowed tools | Phase after target read |
|---|---|---|---|---|
| 1 | `patch_due` | `target_read_due` | `read`, `apply_patch` | `patch_due` |
| 2 | `patch_due` | `target_read_due` | `read`, `apply_patch` | `patch_due` |
| 3 | `patch_due` | `target_read_due` | `read`, `apply_patch` | `patch_due` |

Unit tests also prove that a search hit already covered by a prior read remains `patch_due`.

## Interpretation

This is a sequential before/after engineering gate, not a randomized same-binary A/B: Harness source and manifest hashes necessarily differ. The repeated identical old failure mechanism, deterministic offline phase replay, focused unit tests, and 3/3 real follow-up together support retaining the bounded grace. The result does not establish a general 100% repair rate and should still be checked against older stable bug families for regressions.
