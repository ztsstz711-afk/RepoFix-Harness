# V3.1 revision working set

## Problem

V3.0 showed that shrinking an internal format retry is too late for trajectories that cannot admit the next normal revision request. Two h11 trials stopped with 2,901 and 5,592 tokens remaining before another model call. Their contexts still contained most pre-patch searches and reads even though the latest patch, focused failure, and current source evidence defined a much smaller repair problem.

The historical-average admission floor also reflected earlier 18–23k-character prompts. It could reject a newly compacted prompt based on costs that no longer described the request.

## Revision working set

V3.1 activates a bounded working set only when all of these conditions hold:

- at least one successful `apply_patch` changed a file;
- the latest pytest evidence failed;
- repair phase is `patch_needs_revision` or post-failure `patch_due`.

The model context then keeps:

1. the most recent successful patch at or before the latest failed test;
2. the latest failed `run_command`, or the patch event carrying an automatic failed post-patch test;
3. every event after that failure, including narrow reads, searches, and later edits.

Pre-patch navigation is omitted only from the prompt. `RunState.history`, checkpoints, workspace journals, and evaluation artifacts remain available. `revision_working_set_active` and `revision_working_set_pruned` make the selection auditable.

`patch_due` before the first modification does not activate pruning, so the first patch still has all collected evidence.

## Admission and output allowance

When the working set is active, AgentLoop estimates the next request from the compact current context instead of taking the maximum with the historical per-request average. Provider then estimates the full system/user prompt with a conservative structured-prompt reserve and, near the hard run boundary, reduces only that action's output ceiling. At least 256 output tokens must fit; otherwise no API request is made.

The configured phase ceiling and run-level token limit never increase. Reduced ordinary actions are recorded as `action_output_tokens:<limit>` in provider diagnostics. Format retries retain the independent V3.0 `format_retry_output_tokens:<limit>` diagnostic.

## Frozen real-model gate

The separately frozen gate repeated the same upstream h11 case three times with DeepSeek non-thinking mode, a 60,000-token run budget, at most 12 requests per trial, Docker-isolated pytest, and full `pytest -q h11` acceptance. It did not reuse or combine any previous trial.

| Trial | Verified | Scope | Requests | Tokens | Retries | Estimated cost |
|---|---:|---:|---:|---:|---:|---:|
| 01 | yes | exact | 8 | 45,917 | 0 | $0.02053172 |
| 02 | no | exact | 11 | 54,692 | 0 | $0.02186349 |
| 03 | yes | exact | 9 | 55,219 | 1 format | $0.02218530 |
| **Total** | **2/3** | **3/3** | **28** | **155,828** | **1** | **$0.06458051** |

Trial 01 completed normally after the focused test passed. Trial 03 reached the model-budget boundary after writing a valid patch; the harness independently ran the full suite and accepted 78 passing tests. Trial 02 ended at the token reserve after producing a second changed patch, and final acceptance still failed.

This is the first 60k three-trial h11 gate in V2.8–V3.1 to verify repairs: V2.8, V2.9, and V3.0 each recorded 0/3 under their independently frozen implementations. The comparison is useful engineering evidence, but one 2/3 gate is not a general success-rate estimate.

The failed trajectory exposed a separate state-freshness bug. After a failed focused test, the model wrote a new revision patch; the harness still treated the old failure as evidence about the new code and kept the agent in `patch_needs_revision` instead of requiring verification. That finding defines the next isolated change rather than being folded into the V3.1 result.
