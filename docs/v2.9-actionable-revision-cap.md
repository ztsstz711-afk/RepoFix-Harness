# V2.9 actionable revision cap

## Problem

All three V2.8 60k h11 trials applied an in-scope first patch, ran the focused test, and received a precise traceback ending at the modified `h11/_readers.py` line. The model then used two navigation actions before the existing revision cap forced another patch. Every trial reached token reserve immediately after the second read, so the forced revision request was never admitted.

The V2.8 72k gate showed the same general pattern. Its only successful trial began revising after one read, while other trajectories spent additional requests navigating or encountered budget retries. Globally changing every revision cap from two reads to one would be too aggressive because some failures expose only a test assertion and still need implementation lookup.

## Policy

V2.9 derives the navigation cap from the latest post-patch pytest evidence:

- if the failing output contains a source location for any file actually changed by `apply_patch`, the revision cap is one successful read/search;
- otherwise the cap remains two successful navigation actions;
- a passing test has no revision cap because the phase moves to `verified_patch`;
- full history and test output remain persisted unchanged.

The active cap is stored as `revision_navigation_cap` in every context snapshot. A value of `null` means no failed-patch revision is active.

Once the cap is reached, ContextBuilder returns `patch_due`. The existing Action Registry then exposes only `apply_patch` to both native Function Calling and JSON fallback, so this is an enforced Harness policy rather than prompt advice.

## Deterministic trajectory replay

The three frozen V2.8 60k result histories were replayed without provider calls. Each first patch produced a focused traceback pointing to `h11/_readers.py:172`, followed by two reads.

| Trial | Step 8 after first read | V2.8 step 9 | V2.9 replay step 9 | Active cap |
|---|---|---|---|---:|
| 01 | `patch_needs_revision` | `patch_needs_revision` | `patch_due` | 1 |
| 02 | `patch_needs_revision` | `patch_needs_revision` | `patch_due` | 1 |
| 03 | `patch_needs_revision` | `patch_needs_revision` | `patch_due` | 1 |

Unit coverage also locks the negative case: when the latest failure mentions only `tests/test_parser.py`, one read leaves the phase at `patch_needs_revision` with cap two.

## Scope and next gate

The replay proves that V2.9 changes the intended decision boundary on the recorded failures without weakening the assertion-only path. It does not prove the model will generate a correct second patch. A real-model gate must use a new frozen manifest and report its result separately from V2.8 rather than retroactively modifying the earlier 0/3 and 1/3 measurements.
