# V2.9 actionable revision cap

## Problem

All three V2.8 60k h11 trials applied an in-scope first patch, ran the focused test, and received a precise traceback ending at the modified `h11/_readers.py` line. The model then used two navigation actions before the existing revision cap forced another patch. Every trial reached token reserve immediately after the second read, so the forced revision request was never admitted.

The V2.8 72k gate showed the same general pattern. Its only successful trial began revising after one read, while other trajectories spent additional requests navigating or encountered budget retries. Globally changing every revision cap from two reads to one would be too aggressive because some failures expose only a test assertion and still need implementation lookup.

## Policy

V2.9 derives the navigation cap from the latest post-patch pytest evidence:

- if the failing output contains a source location for any file actually changed by `apply_patch`, the revision cap is one successful read/search;
- otherwise the cap remains two successful navigation actions;
- a passing test has no revision cap because the phase moves to `verified_patch`;
- full history and test output remain persisted unchanged.

The active cap is stored as `revision_navigation_cap` in every context snapshot. A value of `null` means no failed-patch revision is active.

Once the cap is reached, ContextBuilder returns `patch_due`. The existing Action Registry then exposes only `apply_patch` to both native Function Calling and JSON fallback, so this is an enforced Harness policy rather than prompt advice.

## Scope and next gate

The replay proves that V2.9 changes the intended decision boundary on the recorded failures without weakening the assertion-only path. It does not prove the model will generate a correct second patch. The following frozen real-model gate tests that question separately from V2.8.

`evals/upstream-h11-chunk-footer-stability-v2.9.json` repeats the same checksum-qualified h11 case three times with `deepseek-v4-flash`, thinking disabled, 12 requests and 60,000 tokens per trial, Docker isolation, focused iteration, complete 78-test final acceptance, and exact scope limited to `h11/_readers.py`.

The policy worked mechanically: after one post-failure read, all three ninth requests were restricted to `apply_patch`. However, each ninth response violated the active tool contract. A corrective provider retry was then denied because the remaining 6,911–9,528 tokens could not cover the estimated full input plus the 4,096-token patch output ceiling.

Compared with the separately frozen V2.8 60k gate, requests stayed at 27 and verified repairs stayed at 0/3, while total tokens fell from 165,403 to 156,017 (-5.7%). This is an efficiency movement without a success improvement.

## Interpretation

V2.9 removes one unnecessary navigation opportunity but does not make the 60k repair successful. The next bottleneck is provider recovery under a hard residual token budget: retrying with the normal 4,096 patch output ceiling is conservative but leaves otherwise usable budget stranded. Any follow-up must retain the hard run-level limit and reduce only the retry output allowance; simply ignoring the reserve would make evaluation budgets unreliable.
