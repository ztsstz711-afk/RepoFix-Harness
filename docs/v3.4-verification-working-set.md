# V3.4 verification working set

## Problem

V3.3 compacted context after a failed focused test, but restored the full pre-patch history immediately after each new revision patch. The next phase was `patch_needs_verification`, whose policy exposes only focused pytest and Git inspection actions. Old searches, broad reads, previous patches, and superseded failures could not help execute that test, yet five real V3.3 verification prompts were 22–24k characters.

The two failed V3.3 trials then reached token reserve after their second focused test still failed. Reducing verification input earlier in the same trajectories creates room for the actual revision tail without changing run budgets.

## Phase working sets

V3.4 generalizes context selection by phase:

- `verification`: keep the latest successful changed patch and every event after it;
- `revision`: keep the patch associated with the latest current failed test, that failure, and every later event;
- `none`: keep ordinary bounded history selection.

Only the model prompt is pruned. `RunState.history`, checkpoints, workspace journals, and evaluation artifacts remain complete.

New metadata records `phase_working_set_active`, `phase_working_set_kind`, and `phase_working_set_pruned`. Existing `revision_working_set_active` and `revision_working_set_pruned` remain available with their original revision-only meaning. AgentLoop uses the general active flag so a compact verification request is admitted from its current estimate instead of an average dominated by earlier broad navigation calls.

## Frozen real-model follow-up

The real follow-up repeated the same upstream h11 source, task, Docker commands, DeepSeek non-thinking mode, 60,000-token run limit, 12-request limit, and three repetitions. It was a new independent gate and does not alter V3.1–V3.3 results.

|---|---:|---:|---:|---:|---:|---|---:|
| 01 | no | exact | 11 | 59,017 | 1 format | token reserve | $0.02181700 |
| 02 | no | exact | 12 | 56,871 | 0 | request budget | $0.02372614 |
| 03 | no | exact | 12 | 49,017 | 1 format | request budget | $0.01786774 |
| **Total** | **0/3** | **3/3** | **35** | **164,905** | **2** | — | **$0.06341088** |

The real traces confirm the mechanism. First-patch verification prompts were 7,912, 11,249, and 7,244 characters; second-patch verification prompts were 6,568 and 3,335 characters where admitted. These are materially below V3.3's 22–24k verification prompts.

All three trials produced a second changed patch. Trial 01 could not admit its verification request with only 983 tokens remaining. Trials 02 and 03 ran the second focused verification, which still failed, and then reached the request limit. Therefore the context optimization worked but did not improve this sampled success outcome. The next experiment should reduce explicit model calls spent selecting deterministic post-patch verification, not continue trimming already compact verification prompts.

## Independent auto-verification follow-up

A separate configuration follow-up kept the V3.4 Harness and all case, model, source, command, request, and token settings fixed, changing only `verify_after_patch=true`. Harness therefore executed focused pytest immediately after each changed patch without spending a model request to select `run_command`.

| Trial | Verified | Scope | Requests | Tokens | Retries | Failure | Estimated cost |
|---|---:|---:|---:|---:|---:|---|---:|
| 01 | no | exact | 11 | 58,290 | 2 format | token reserve | $0.01981464 |
| 02 | no | exact | 9 | 53,389 | 1 format | token reserve | $0.02331711 |
| 03 | no | exact | 8 | 51,159 | 1 format | token reserve | $0.02377423 |
| **Total** | **0/3** | **3/3** | **28** | **162,838** | **4** | — | **$0.06690598** |

The follow-up reduced model requests from 35 to 28 but did not materially reduce total tokens or produce a verified repair. Trial 02 was denied with 6,611 tokens left because AgentLoop's compact-context estimate was 6,758 tokens—a 147-token gap—before Provider had an opportunity to apply its residual output ceiling. Trial 03 had 8,841 left against a 9,497 estimate. These are direct evidence for refining admission of already compact working-set requests while retaining Provider's hard-limit check.
